# Architecture — 설계 판단 기준

> 비유: `coding-style.md`가 "문장을 어떻게 쓰나"라면, 이 문서는 "장을 어떻게 나누나"다.
> 크기 규칙(800줄/50줄)은 *얼마나 크게 쓰지 마라*지 *어떻게 나눌 것인가*가 아니다.

언어와 무관한 **판단 기준**만 담는다. 언어 관용구는 `architecture-{ts,py}.md`,
프로젝트 폴더 구조는 각 프로젝트 `.claude/rules/`에 둔다.

## 1. 의존성 방향 — 안쪽으로만

정책(비즈니스 규칙)은 입출력을 몰라야 한다. 반대는 안 된다.

```
UI · API · CLI  →  유스케이스  →  도메인 규칙
DB · 외부 API   →  (어댑터)   ↗
```

- 도메인 코드가 DB 드라이버·HTTP 클라이언트·프레임워크 타입을 import 하면 방향이 뒤집힌 것이다
- 뒤집을 수 없으면 인터페이스를 도메인 쪽에 두고 바깥에서 구현한다
- 판정법: **도메인 로직만 떼어 단위 테스트가 되는가.** 안 되면 방향이 틀렸다

## 2. 공통화 — 언제 하고, 언제 하지 않나

가장 자주 틀리는 판단이라 기준을 명시한다.

**한다** (셋 다 충족)

1. 같은 로직이 **3번째** 등장했다 (2번은 우연일 수 있다)
2. 세 곳이 **같은 이유로 함께 변한다** — 요구사항이 바뀌면 셋 다 바뀐다
3. 추출 후 **호출부가 더 읽기 쉬워진다**

**하지 않는다**

- **우연한 중복** — 모양만 같고 변하는 이유가 다르다. 합치면 나중에 억지로 분기가 생긴다
- **위임만 하는 헬퍼** — 한 줄 호출을 다른 한 줄 호출로 바꾸는 래퍼는 간접 계층만 늘린다
- **선점 추상화** — 두 번째 사례가 아직 없는데 "나중에 쓸 것 같아서" 만드는 것

**검증**: 추출한 뒤 호출부를 다시 읽는다. 이해가 더 어려워졌으면 **되돌린다.**
공통화의 편익은 중복 제거이고 비용은 간접 계층이다. 비용이 크면 중복이 낫다.

## 3. 추출은 동작 불변으로

기존 코드를 공용 모듈로 옮길 때는 **순수 이동**과 **동작 변경**을 같은 커밋에 섞지 않는다.

1. 이동만 한다 → 기존 테스트가 그대로 통과해야 한다
2. 통과를 확인한 뒤에 동작을 바꾼다

섞으면 테스트가 깨졌을 때 이동 탓인지 변경 탓인지 알 수 없다.

## 4. 테스트 결정성 — 비결정 요소는 주입한다

현재 시각·난수·환경변수·파일시스템은 **인자로 받는다**. 함수 안에서 직접 읽지 않는다.

- 나쁨: 함수 안에서 오늘 날짜를 읽어 "최근 3년"을 계산 → 내년에 테스트가 깨진다
- 좋음: 기준일을 인자로 받는다 → 호출부가 실제 오늘을, 테스트가 고정일을 넘긴다

순수 함수로 만들 수 있는 계산은 순수 함수로 분리한다. 부수효과는 바깥 얇은 층에만 둔다.

## 5. 폐기 결정을 기록한다

**도입했다가 버린 것은 "왜 버렸는지"를 문서에 남긴다.** 안 남기면 6개월 뒤에 같은 것을 다시 만든다.

기록 위치는 해당 프로젝트의 도메인 문서. 형식은 한 줄이면 충분하다:

> `MonospaceText`(표시폭 계산 유틸)은 도입했다가 **폐기**했다 — 데스크톱 폰트에서 폭이 안 맞는다. **다시 만들지 말 것.**

## 6. 기존 부채는 이번 변경과 분리한다

이번에 손대는 줄만 고친다. 옆에 있는 낡은 코드는 눈에 띄어도 같은 커밋에서 정리하지 않는다
(golden-principles #12 수술적 변경). 부채는 별도로 기록하고 별도 커밋으로 처리한다.

- 예: 825줄짜리 파일에서 3줄만 바꾸는 작업이라면, 파일 분할은 이번 범위가 아니다
